MIDI Monitor

View incoming notes, controllers, channels, pitch bend, clock, and transport. Newest messages appear first. The main display provides a cross-reference for hardware settings and MIDI implementation charts.

Controls

  • Reset: clear message history
  • Freeze: hold the captured history; incoming messages are discarded while frozen
  • Format off — MIDI 1.0: show familiar MIDI 1.0 values and status/data bytes
  • Format on — MIDI 2.0: show full received value resolution and UMP hexadecimal words

Format updates the existing history immediately, including while frozen. It changes the display, not incoming MIDI or its meaning.

Incoming data

Column Meaning
Gr UMP group, 1–16; dash when not applicable
Ch MIDI channel, 1–16; dash for non-channel messages
Msg Message type, including controller or program number
Val Note, velocity, pressure, controller value, pitch bend, or position
Hex MIDI 1.0 status/data bytes with Format off; received UMP words with Format on

There are 26 visible rows, with up to 128 messages retained. Long entries are shortened to fit. Invalid packets are highlighted with an error message.

MIDI 1.0 values

  • Notes, velocity, CC, and pressure: 0–127
  • Pitch bend: 0–16383, centered at 8192
  • Program numbers: 0–127; hardware may label them 1–128
  • Note 60 = C4; compare note numbers when hardware uses different octave names

Pitch bend shows one unsigned value. At the endpoints and center it adds (min), (center), or (max). It does not infer semitones, since bend range depends on the receiving instrument.

For MIDI 2.0 packets, MIDI 1.0 display values use the upper 7 bits of velocity, pressure, CC, and absolute controller values; bend uses the upper 14 bits. Notes, programs, attributes, flags, and relative controller deltas are unchanged. Incoming MIDI 1.0 values remain unchanged in either display mode.

Hex for hardware reference

With Format off, Hex shows bytes such as 90 40 64: Note On, channel 1, note 64, velocity 100. Pitch bend center on channel 1 appears as E0 00 40.

When Audulus supplies MIDI 2.0 packets, these MIDI 1.0 bytes are reconstructed from the displayed values. They are not a recording of the original hardware bytes. Program Change shows the program message; bank information remains in Val. Messages without a supported MIDI 1.0 conversion show a dash.

MIDI 1.0 zero-velocity Note On means Note Off. MIDI 2.0 zero-velocity Note On remains Note On; Hex shows a dash if conversion would incorrectly turn it into Note Off.

MIDI 2.0 values

Note velocity uses 0–65535. Controllers, pressure, and bend use unsigned 32-bit values; bend center is 2147483648. Per-note controllers, registered/assignable controllers, note attributes, and management flags are displayed where decoded.

Detail table

A full-width readable line below the history shows the newest captured message, including channel, message type, and decoded value. The compact packet table sits beneath it. Both use text size 0.8.

Heading Meaning
Format Selected display mode: MIDI 1.0 or MIDI 2.0
Word 1 / Word 2 Actual received UMP words, each eight hexadecimal digits
Offset Sample position within the audio processing block; not an absolute timestamp

The detail words always preserve the received packet, regardless of Format. A missing word shows a dash. Additional word columns appear for longer packets.

MIDI 1.0 hardware can arrive through Audulus encoded as MIDI 2.0 UMP. Two received words therefore do not establish that the hardware itself uses MIDI 2.0. UMP groups provide an additional routing layer, with 16 MIDI channels per group.

Capture limits

  • At most 32 events per audio block are forwarded to Canvas; a full Canvas queue can also drop display events
  • MIDI 1.0 high-resolution CC pairs and RPN/NRPN sequences are shown separately, not assembled
  • Utility, SysEx/data, Flex, Stream, and unsupported packets are identified where possible but are not fully decoded or assembled
  • Unsupported packets have no MIDI 1.0 Hex conversion; use MIDI 2.0 display mode to inspect their raw words
  • Only packets supplied by Audulus can appear; this monitor does not identify the source device

Notes

Lyte receives MIDI with receive_ump(), which carries MIDI 1.0 and MIDI 2.0 packets through one queue. Audulus may encode MIDI 1.0 hardware input as MIDI 2.0 UMP. The monitor can identify the received encoding, but cannot recover which encoding the source hardware originally used. Format selects the display representation; the detail words always show the actual received packet.

A UMP group provides an extra routing layer with 16 MIDI channels per group. Groups appear as 1–16 in the monitor, while the script API uses 0–15. Offset is supplied by the receiver as a sample position within the current audio block.

Clock and transport have no MIDI channel. MIDI System Reset is an incoming message and does not clear the monitor’s history; use the Reset control to clear history. Reserved MIDI 1.0 statuses F4, F5, F9, and FD are flagged if received. Route or isolate devices in Audulus, the host, or an external MIDI utility when troubleshooting one source.
